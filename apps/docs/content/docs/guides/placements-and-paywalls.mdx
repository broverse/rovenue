A **placement** is a named location in your app — `onboarding_end`,
`settings_upsell`, `feature_gate` — where a paywall may appear. Your code asks
for the placement by its identifier; the dashboard decides what to show there:
which paywall, to which audience, or which A/B-test variant. Change the
paywall, retarget the audience, or start a test without shipping an update.

A **paywall** in Phase A is a *remote-config paywall*: you author free-form
JSON per locale in the dashboard and render the UI yourself. Rovenue serves
the config, the offering (products and packages), the experiment assignment,
and wires up analytics and purchase attribution automatically.

<Callout type="info">
`getPaywall` returns `null` when the placement resolves to nothing — it was
retired, targeted to "show nothing", or the identifier is unknown. This is
deliberate: a shipped app must never crash because a placement changed
server-side. Always handle the `null` branch.
</Callout>

### Types on this page

```ts
type Paywall = {
  placementIdentifier: string;          // the placement you asked for
  placementRevision: number;            // bumps on every dashboard edit
  paywallIdentifier: string | null;     // dashboard identifier of the paywall
  paywallName: string | null;
  configFormatVersion: number;
  remoteConfig: Record<string, unknown> | null; // your JSON, resolved for the locale
  remoteConfigLocale: string | null;    // which locale was resolved
  offering: Offering | null;            // standard offering with packages
  presentedContext: PresentedContext | null; // attribution — handled for you
};
```

The optional `locale` selects which localization of the remote config you
receive. If the requested locale isn't configured, the paywall's default
locale is served; `remoteConfigLocale` tells you which one you got.

<Callout title="Builder paywalls resolve the locale on the device">
A **builder** paywall ships every localization in its payload, so the
`?locale` query parameter only slices the legacy `remoteConfig` field. Which
language a buyer sees is decided on the device, from the `locale` you pass to
`getPaywall` / the paywall view.

Text resolves by **language**, not by exact tag: the requested tag is tried
first, then each shorter prefix, then the paywall's default locale. So
`pt-BR` finds a `pt` table, and `zh-Hans-CN` finds `zh-Hans` and then `zh`.
Matching is case-insensitive, because BCP-47 tags are. Pass the device locale
as the device reports it — you do not need to normalise it first.
</Callout>

## How a placement resolves

In the dashboard a placement is an ordered list of audience rows. The first
row whose audience matches the subscriber wins:

1. **Paywall** — that paywall is returned directly.
2. **A/B test** — a running `PAYWALL` experiment; the SDK deterministically
   draws a variant (same subscriber + same experiment ⇒ same variant, every
   time, on every device, even offline from cache) and returns that variant's
   paywall. Exposure is reported automatically.
3. **Nothing** — `getPaywall` returns `null` for this audience.

An "All users" row at the bottom acts as the catch-all; without one,
non-matching subscribers get `null`.

## Tracking and attribution

- Call `logPaywallShown(paywall)` when the paywall actually becomes visible.
  This emits a `paywall_view` event; views and unique views appear on the
  placement's page in the dashboard.
- Purchase attribution is automatic: the paywall carries a
  `presentedContext` snapshot, and the SDK attaches it to the next purchase.
  Revenue is credited to the placement, paywall, and variant that converted
  the subscriber. You never construct or send this yourself.

<Callout type="warn">
`logPaywallShown` is a best-effort analytics beacon — it never throws and
never blocks your UI. Call it once per presentation, not per render.
</Callout>

## Offline behavior

The last successful response for each placement is cached on device. On
network failure the cached response is served, and because variant selection
is deterministic, a cached A/B test still yields the same variant the server
would have assigned.

## Relationship to offerings

A paywall references an offering; `paywall.offering` is the same hydrated
shape returned by [`getOfferings()`](/docs/guides/processing-purchases) —
pass any of its packages straight into `purchase(pkg)`. Placements do not
replace offerings; they decide *which* paywall (and therefore which
offering) a given subscriber sees at a given location.

## Builder paywalls (web)

In Phase B, paywalls can carry a **`builderConfig`** — a platform-neutral
component tree authored visually in the dashboard (Paywalls → Open builder).
This config appears in the placement payload with `configFormatVersion: 2`
when non-null; the `?locale` query parameter continues to slice only the
`remoteConfig` field, so builder localizations ship whole.

Web apps render builder paywalls using the `@rovenue/paywall-renderer`
package:

On the web there is no SDK façade yet — fetch the placement over REST with
your public API key and pass the payload straight into the renderer. (On
iOS/Android/React Native you don't do any of this: `getPaywall()` returns
the paywall with its builder config and the platform renderers below draw
it directly.)

```tsx
import { PaywallRenderer } from '@rovenue/paywall-renderer';

const res = await fetch(`${API_URL}/v1/placements/onboarding_end`, {
  headers: { Authorization: `Bearer ${PUBLIC_KEY}` },
});
const { data } = await res.json();

if (data.paywall?.builderConfig) {
  <PaywallRenderer
    config={data.paywall.builderConfig}
    offering={data.paywall.offering}
    locale="en"
    colorScheme="light"
    priceView={/* formatted price strings per package */}
    onPurchase={(packageId) => { /* handle purchase */ }}
    onClose={() => { /* dismiss */ }}
    onUrl={(url) => { /* open link */ }}
  />
} else if (data.paywall?.remoteConfig) {
  // Fall back to rendering the remote-config JSON yourself
}
```

**Props contract:**
- `config` — the builder config from the paywall payload
- `offering` — the paywall's offering (hydrated packages with displayName,
  metadata, storeIds)
- `locale` (optional) — which localization of text keys to resolve (defaults
  to config's defaultLocale)
- `colorScheme` — "light" or "dark" for theme-aware rendering
- `priceView` (optional) — formatted price strings keyed by packageIdentifier
  (`{ price: string; pricePerPeriod: string; period: string }`); enables
  `{{price}}` and other variables in text; dashboard preview passes
  placeholder views; web consumers supply real store-formatted prices
- `onPurchase` — callback when the user taps a package and confirms purchase
- `onClose`, `onRestore`, `onUrl` (optional) — action callbacks; restore
  button is hidden when `onRestore` is not supplied
- `data-rov-node` attributes — every rendered node carries a stable ID for
  testing and custom styling; this is a documented feature

## Native rendering (iOS & Android)

Builder paywalls render **natively** — no webview — with variables like
`{{price}}` fed by real store pricing (StoreKit / Play Billing). Both
renderers auto-track the view (`paywall_view`) on first appearance; you do
not call `logPaywallShown` for builder paywalls. Semantics match the web
renderer: unknown components render their fallback (or nothing), the
restore button is hidden when you supply no restore handler, and URLs are
handed to your callback — the renderer never opens them itself.

paywall is drawn by exactly the same code an iOS or Android app runs:

## Lottie animations

A builder paywall can contain a **`lottie`** node. The Rovenue SDKs ship
**no Lottie runtime** — not `lottie-ios`, not `com.airbnb.android:lottie`,
not `lottie-web`. Bundling one would force every app that never uses a
Lottie node to carry it. Instead your app registers whichever player it
already ships, once, and the renderer hands that player one request per
`lottie` node.

With no player registered a `lottie` node draws its **`fallback`** node if
the author gave it one, and otherwise nothing — the same "cannot draw this"
path every other node type already takes, not a crash and not a blank
paywall.

### The request contract

Every platform hands the host the same five values:

| Field | Meaning |
|---|---|
| `url` | The theme-resolved animation source (the light or dark URL, picked for the active color scheme). |
| `loop` | Author's loop setting. Absent in the config = `true`. |
| `autoplay` | Author's standing instruction from the builder. Absent = `true`. |
| `speed` | Playback rate multiplier. Absent = `1`. |
| `playing` | The SDK's moment-to-moment verdict: this node is on screen **and** the app is in the foreground. |

Two things are worth reading twice before you write the host renderer:

- **`playing` is not `autoplay`.** `autoplay` is authored once in the
  dashboard and never changes for the life of the paywall. `playing` comes
  from the same shared visibility signal that `video`, `carousel` and
  `countdown` use, and it flips as the paywall scrolls or the app goes to
  the background. A correct host renderer honours both: it must not start on
  its own when `autoplay` is `false`, and it must pause when `playing` goes
  `false`. Every snippet below derives one boolean from the pair for exactly
  this reason.
- **Registration is process-level and happens once**, at startup, well
  before any paywall is presented. It is not per-view configuration and
  there is no per-paywall override. Passing `nil` / `null` unregisters.

One deliberate asymmetry: `url` is a `URL` on iOS and a `String` on Android
and web. That is not an oversight — it is what each platform's Lottie
library actually takes (`lottie-ios` wants a `URL`, `lottie-android`'s
`setAnimationFromUrl` wants a `String`). On iOS a source that cannot be
turned into a `URL` produces no request at all, so the node takes the
ordinary fallback path.

<Callout type="warn">
The registry is global process state, so it **leaks across tests**. Any test
that registers a renderer must unregister it (pass `nil` / `null`) in its
teardown.
</Callout>

### Register a player

<Tabs items={['Swift', 'Kotlin', 'React Native', 'Web']}>
<Tab value="Swift">

```swift
import Rovenue
import SwiftUI
import Lottie   // your app's own dependency — Rovenue does not ship it

@main
struct MyApp: App {
    init() {
        // Process-level, once, before any paywall is presented.
        registerLottieRenderer { request in
            // ── Rovenue side: exact. ──────────────────────────────────
            // request.url      URL     theme-resolved source
            // request.loop     Bool
            // request.autoplay Bool    author's standing instruction
            // request.speed    Double
            // request.playing  Bool    on screen AND app in front
            let shouldPlay = request.autoplay && request.playing

            // ── Host side: your player. Adapt these calls to the
            //    version of lottie-ios you actually ship. ─────────────
            return AnyView(
                LottieView { try await LottieAnimation.loadedFrom(url: request.url) }
                    .looping(request.loop)
                    .animationSpeed(request.speed)
                    .paused(!shouldPlay)
            )
        }
    }

    var body: some Scene { WindowGroup { ContentView() } }
}
```

The signature you are conforming to is:

```swift

    public let url: URL
    public let loop: Bool
    public let autoplay: Bool
    public let speed: Double
    public let playing: Bool
}

public typealias LottieRenderer = (LottieRenderRequest) -> AnyView
public func registerLottieRenderer(_ render: LottieRenderer?)
```

Returning `AnyView(EmptyView())` is a legitimate "draw nothing right now".

- **iOS** — `ios/<YourApp>/AppDelegate.swift`, inside

- **Android** — `android/app/src/main/java/.../MainApplication.kt`, inside

does not help here: the paywall is not drawn by React, so a React component
cannot render into it. `lottie-react-native` does bring the two native
libraries in transitively, so if you already depend on it you can register
against those directly from the native entry points above.

## Footer links

Every shipping paywall ends with the same row of fine print — Restore
Purchases, Terms, Privacy. `footerLinks` is that row as one node, rather than
a stack of small buttons:

```json
{
  "type": "footerLinks",
  "id": "footer",
  "links": [
    { "labelKey": "f_restore", "action": { "kind": "restore" } },
    { "labelKey": "f_terms",   "action": { "kind": "url", "url": "https://example.com/terms" } },
    { "labelKey": "f_privacy", "action": { "kind": "url", "url": "https://example.com/privacy" } }
  ],
  "separator": "dot",
  "align": "center"
}
```

- `links` — 1 to 5 entries. Each carries a localized `labelKey` and the same
  `action` union a `button` node uses: `restore`, `url`, or `close`.
- `separator` — `"dot"` (`·`, the default), `"pipe"` (`|`), or `"none"`.
- `align` — `"start"`, `"center"` (the default), or `"end"`.
- `color` — applies to both the labels and the separators.

The row **wraps** when it does not fit, and the separators are drawn between
the links that actually render:

- A `restore` link is hidden when the host supplies no restore handler, the
  same rule a `button` node follows — an inert Restore control implies restore
  is possible when it is not.
- A link whose label does not resolve is hidden.
- Separators are computed over the surviving links, so there is never a
  leading, trailing or doubled separator. If every link is hidden, the node
  renders its `fallback`, or nothing.

Separators are hidden from screen readers: the row reads as N links.

## Localization workflow

Builder paywall text is key-based. Each text-bearing node carries a key, and
`localizations[locale][key]` holds the string, so a paywall's copy travels
with it as one self-contained blob.

**Adding a language.** The builder's locale picker searches the App Store
localization set and labels each entry in English. A code the list does not
carry can still be typed in, for anywhere the stores do not localize their own
listings.

**Auto-translate.** In the Localization matrix, each language column has a
Translate button. By default it fills only that column's *empty* cells from
the base locale — translations you have already reviewed are never overwritten.
Replacing a whole column is a separate, two-click confirm. Individual cells can
be translated one at a time, and one undo reverts a whole run.

<Callout type="warn" title="Placeholders are preserved, or the string is not translated">
Paywall copy interpolates the selected package's values — `{{price}}`,
`{{period}}`, `{{packageName}}` and friends. An unknown placeholder renders
**verbatim**, so a translation that renamed `{{price}}` would show literal
braces to a paying customer and nothing downstream would notice.

Every translation is therefore checked against its source: it must carry the
same placeholders, the same number of times (order may change — languages
reorder clauses). A string that fails is retried once, and if it fails again
it is **left untranslated** and reported by name. A missing translation falls
back to the base locale and reads correctly; a corrupted one does not.
</Callout>

Cells filled by auto-translate are marked until you edit them, so a reviewer
can see what no human has read yet.

## Offline fallback file

Builder paywalls and placements can work offline using a bundled fallback file. This file contains the serialized configuration for all active placements, resolved with empty attributes. On network failure or during app startup before the first successful fetch, the cached fallback provides a complete, deterministic experience.

### Export the fallback file

The dashboard exports a fallback file containing all active placements:

```bash
# GET /dashboard/projects/:projectId/paywalls/fallback-export
# Downloads rovenue-fallback.json (Content-Disposition attachment)
curl -H "Authorization: Bearer <user_session_token>" \
  https://dashboard.rovenue.app/dashboard/projects/proj_123/paywalls/fallback-export \
  > rovenue-fallback.json
```

The file format is a JSON array of resolved placement envelopes, one per active placement identifier.

When `getPaywall(placementId)` runs, it tries network first, then cache, then fallback. The returned paywall carries a `servedFromFallback: boolean` flag so your app can react if needed (e.g., disable purchase buttons, show a sync notice). A/B test variant selection remains deterministic from the fallback — the same subscriber + experiment always draws the same variant, even offline.

## Conditional styling (overrides)

Builder paywalls support per-node conditional overrides. In the Paywalls builder, click a node's **Overrides** section to add styling changes that apply when:

- **Intro Eligible** — the user can purchase an introductory offer (iOS/Android only; web is always false).
- **Selected** — the cell is the user's selected choice in a package list (only inside `cellTemplate` nodes).

Each override specifies visual properties (color, background, cornerRadius, align, spacing, style) to apply conditionally. Overrides are merged in order, so later ones win.

### Cell templates

When authoring a package list cell, you can define a `cellTemplate` — a reusable node tree that renders **once per package**. This enables rich, per-package styling without duplicating nodes.

In the builder:

1. Click the package list node.
2. In the properties panel, find **Cell Template**.
3. Design the template node tree (buttons, text, badges, etc.).
4. Apply overrides to nodes *inside* the template to customize per package or state.

The template renders inside each cell's pressable wrapper, with cell-scoped variables like `{{price}}` resolved per package. Unknown node types fallback gracefully; malformed templates cause a decode error (blocks publish until fixed).

## Variables

Builder paywalls support variable substitution in text. Variables are surrounded by double braces: `{{variableName}}`. If a variable is absent or unsupported by the platform, the placeholder text is left verbatim.

| Variable | Type | Platform | Notes |
|---|---|---|---|
| `{{price}}` | string | Web, iOS, Android, RN | Formatted price (e.g., "$9.99" or "€9,99"). Requires priceView on web. |
| `{{pricePerPeriod}}` | string | Web, iOS, Android, RN | Price per billing period (e.g., "$2.49/month"). |
| `{{period}}` | string | Web, iOS, Android, RN | Billing period (e.g., "month", "year"). |
| `{{pricePerDay}}` | string | Web, iOS, Android, RN | Price per day (e.g., "$0.33/day"). |
| `{{pricePerWeek}}` | string | Web, iOS, Android, RN | Price per week (e.g., "$1.92/week"). |
| `{{pricePerMonth}}` | string | Web, iOS, Android, RN | Price per month (e.g., "$8.33/month"). |
| `{{pricePerYear}}` | string | Web, iOS, Android, RN | Price per year (e.g., "$99.99/year"). |
| `{{introPrice}}` | string | iOS, Android | Formatted intro offer price; absent if no intro offer. |
| `{{introPeriod}}` | string | iOS, Android | Intro offer period (e.g., "3 days", "1 month"). |
| `{{relativeDiscount}}` | string | Web, iOS, Android, RN | Discount percentage (e.g., "33%") relative to the yearly price; absent if N/A. |

Native platforms (iOS/Android) derive these from real store pricing (StoreKit, Play Billing). Web requires optional `priceView` props passed to the renderer. If a platform does not supply a variable's value, the placeholder remains unchanged in the rendered text (e.g., "Save `{{relativeDiscount}}`" shows literally if the discount is unknown).

## Events

Builder paywalls and placements emit analytics events on all platforms.

### Paywall shown

Paywalls displayed via `getPaywall()` + your custom rendering emit a `paywall_view` event when you call:

```ts
logPaywallShown(paywall)
```

Views and unique viewers appear on the placement's dashboard page.

<Callout type="warn">
This is a best-effort beacon; call it once per presentation, not per render.
</Callout>

### Paywall closed

All renderers (web, native, RN) automatically emit a `paywall_close` event when the paywall is dismissed. You can also log a close manually:

<Tabs items={['Swift', 'Kotlin', 'React Native']}>
<Tab value="Swift">

```swift
Rovenue.shared.logPaywallClosed(paywall)
```

</Tab>
<Tab value="Kotlin">

```kotlin
Rovenue.shared.logPaywallClosed(paywall)
```

</Tab>
<Tab value="React Native">

```ts
import { Rovenue } from '@rovenue/react-native-sdk';

Rovenue.logPaywallClosed(paywall);
```

</Tab>
</Tabs>

Paywall events ride a **durable, at-least-once queue** on the device. Events survive process kills and retries automatically on network recovery. If the server returns 5xx or network fails, the event stays queued; on 2xx, it's removed. This guarantees every close is eventually reported, even if the user dismisses the paywall and immediately closes the app.
