Every Rovenue SDK error originates from the same Rust-core `RovenueError` type and is mapped to an idiomatic type on each platform:

- **React Native** — thrown as `RovenueError` (a class extending `Error`) with a `kind` discriminant. Use `e.kind === "..."` to branch.
- **Swift** — thrown as `RovenueError` (a struct conforming to `LocalizedError`) with a `kind: ErrorKind` discriminant. Catch with `catch let e as RovenueError`.
- **Kotlin** — thrown as `RovenueException` (a plain class, not sealed) with a `kind: ErrorKind` discriminant. There is no per-kind subclass and no exhaustive `when` over it — catch `RovenueException` and branch on `e.kind`.

Calling the HTTP API directly instead of through an SDK? See [API Errors](/docs/reference/api-errors) for the `{ error: { code, message } }` envelope's `code` values — a different, larger set than the `kind`s below.

## Migrating from 0.15.x → 0.16.0

<Callout type="warn">
**Breaking change in 0.16.0** — the per-type error subclasses and Swift `Rovenue.Error` enum cases are replaced by a single `RovenueError`/`RovenueException` with a `kind` string discriminant, and `.pending` purchases are now a non-throwing `Deferred` outcome.
</Callout>

### React Native: `instanceof` → `e.kind`

```ts
// Before (0.15.x)
import { InsufficientCreditsError, NetworkUnavailableError } from '@rovenue/react-native-sdk';
try {
  await Rovenue.purchase(pkg);
} catch (e) {
  if (e instanceof InsufficientCreditsError) { /* … */ }
  if (e instanceof NetworkUnavailableError) { /* … */ }
}

// After (0.16.0)
import { RovenueError } from '@rovenue/react-native-sdk';
try {
  const result = await Rovenue.purchase(pkg);
  if (result.isDeferred) {
    // Ask-to-Buy / parental controls — not an error, poll or wait for the
    // PURCHASES_UPDATED listener before granting entitlements.
    showToast('Your purchase is awaiting approval.');
    return;
  }
} catch (e) {
  if (e instanceof RovenueError) {
    if (e.kind === 'InsufficientCredits') { /* … */ }
    if (e.kind === 'NetworkUnavailable') { /* … */ }
  }
}
```

### Swift: `Rovenue.Error` enum → `RovenueError` struct

```swift
// Before (0.15.x)
do {
  try await Rovenue.shared.purchase(pkg)
} catch Rovenue.Error.purchasePending { showToast("Awaiting approval.") }
  catch Rovenue.Error.insufficientCredits { /* … */ }

// After (0.16.0)
do {
  let result = try await Rovenue.shared.purchase(pkg)
  if result.isDeferred { showToast("Awaiting approval."); return }
} catch let e as RovenueError {
  switch e.kind {
  case .insufficientCredits: /* … */
  default: throw e
  }
}
```

### Kotlin: standalone exceptions → `RovenueException.kind`

```kotlin
// Before (0.15.x)
try {
  Rovenue.shared.purchase(activity, pkg)
} catch (e: PurchasePendingException) { showToast("Awaiting approval.") }
  catch (e: PurchaseCancelledException) { /* user cancelled */ }

// After (0.16.0)
val outcome = Rovenue.shared.purchase(activity, pkg)
if (outcome.isDeferred) { showToast("Awaiting approval."); return }
// Errors:
try {
  Rovenue.shared.purchase(activity, pkg)
} catch (e: RovenueException) {
  when (e.kind) {
    ErrorKind.PURCHASE_CANCELED -> { /* user cancelled — no action */ }
    else -> throw e
  }
}
```

### Handling the Deferred purchase state

`purchase()` no longer throws for Ask-to-Buy / parental-control holds. Instead, it returns a `StorePurchaseOutcome` with `isDeferred = true`. You should:

1. Show a friendly message (e.g. "Your purchase is awaiting approval from your family organizer.").
2. Do **not** grant entitlements — entitlements are only granted after the purchase completes asynchronously.
3. Listen for the `PURCHASES_UPDATED` notification (RN: `Rovenue.addPurchasesUpdatedListener`; Swift: `RovenueDelegate.purchasesDidUpdate`; Kotlin: `PurchasesUpdatedListener`) to know when the deferred purchase resolves.

## Calling the SDK before `configure()`

This is **not** an entry in the table below — it isn't part of the `ErrorKind` taxonomy
at all, and it is not something to write a `catch` for. Calling any other SDK method
before `configure()` has run is a programming error to fix at the call site (always
`configure()` first, at app startup — see [App lifecycle](/docs/guides/app-lifecycle)),
not a runtime condition your code should branch on. What actually happens if you get
the ordering wrong, per platform:

- **iOS** (native Swift, and React Native / Flutter on iOS, which call into the same
  Swift singleton) — a **hard crash**. Accessing `Rovenue.shared` before `configure()`
  triggers Swift's `fatalError`, which aborts the process immediately. This is not a
  throwable Swift error: no `do`/`catch` in Swift, no `try`/`catch` in JS, and no
  `try`/`catch` in Dart can intercept it — the crash log will show `"Rovenue: must
  call Rovenue.configure(apiKey:baseUrl:) before accessing shared"` just before the
  process terminates.
- **Android** (native Kotlin) — throws a plain `IllegalStateException`, **not** a
  `RovenueException`. A `catch (e: RovenueException)` will not observe it at all; you'd
  need a broader `catch (e: Exception)` to see it, and even then it carries no
  `ErrorKind` — it's outside the taxonomy this page documents.
- **React Native on Android** and **Flutter on Android** — the native bridge on this
  platform catches everything and re-surfaces it as a normal, catchable error, but
  because the underlying `IllegalStateException` isn't a `RovenueException`, it
  normalizes to the generic `kind: "Internal"` (RN) / `RovenueErrorKind.internal`
  (Flutter) — indistinguishable from any other unexpected internal failure, not a
  signal you can branch on to detect "not configured" specifically.

The only reliable fix is ordering: call `configure()` before anything else, every time.

## Error table

| When it fires | React Native (class) | Swift (enum case) | Kotlin (exception) |
|---------------|---------------------|-------------------|--------------------|
| API key is missing, malformed, or rejected by the server | `InvalidApiKeyError` | `.invalidApiKey` | `RovenueException.InvalidApiKey` |
| An argument was invalid — e.g. an empty string passed to `identify()` | `InvalidArgumentError` | `.invalidArgument` | `RovenueException.InvalidArgument` |
| Server returned a non-recoverable error response | `ServerError` | `.serverError` | `RovenueException.ServerException` |
| Device has no network connectivity | `NetworkUnavailableError` | `.networkUnavailable` | `RovenueException.NetworkUnavailable` |
| Request exceeded the allowed time limit | `TimeoutError` | `.timeout` | `RovenueException.Timeout` |
| Too many requests — SDK is being rate-limited; back off and retry | `RateLimitedError` | `.rateLimited` | `RovenueException.RateLimited` |
| Local persistent storage (MMKV) read/write failure | `StorageError` | `.storage` | `RovenueException.Storage` |
| Returned by the server when a virtual-currency spend transaction has insufficient balance (server-side API only — no client SDK method throws this) | `InsufficientCreditsError` | `.insufficientCredits` | `RovenueException.InsufficientCredits` |
| Receipt could not be validated by the store or server | `ReceiptInvalidError` | `.receiptInvalid` | `RovenueException.ReceiptInvalid` |
| Unexpected internal SDK error | `InternalError` | `.internalError` | `RovenueException.Internal` |
| User cancelled the store purchase sheet | `PurchaseCancelledError` | `.purchaseCancelled` | `PurchaseCancelledException` |
| Purchase is pending approval (Ask-to-Buy / parental controls) | `PurchasePendingError` | `.purchasePending` | `PurchasePendingException` |
| The selected product is not available in the user's storefront | `ProductNotAvailableError` | `.productNotAvailable` | `ProductNotAvailableException` |
| The store returned a non-specific billing or connectivity error | `StoreProblemError` | `.storeProblem` | `StoreProblemException` |

<Callout type="warn">
**`InvalidApiKeyError` vs `InvalidArgumentError`**

`InvalidApiKeyError` fires when the SDK detects that your API key is malformed (wrong prefix) at `configure()` time, or when the server rejects it on the first network request. It indicates a **configuration problem** — check your dashboard key.

`InvalidArgumentError` fires when your code passes an invalid value to a method at call time — for example, an empty string to `identify()`. It indicates a **programming error** in your call site.
</Callout>

## Handling errors

All throwing SDK methods should be wrapped in try/catch. The recommended pattern is to handle the errors you expect explicitly, then re-throw anything unexpected so it surfaces in your crash reporting.

<Tabs groupId="platform" persist items={['React Native', 'Swift', 'Kotlin']}>
  <Tab value="React Native">
    ```ts
    import {
      Rovenue,
      PurchaseCancelledError,
      PurchasePendingError,
      ProductNotAvailableError,
      ReceiptInvalidError,
      NetworkUnavailableError,
    } from '@rovenue/react-native-sdk';

    // --- Purchase flow ---
    try {
      const result = await Rovenue.purchase(pkg);
      // success
    } catch (e) {
      if (e instanceof PurchaseCancelledError) {
        // User dismissed the store sheet — no action needed
      } else if (e instanceof PurchasePendingError) {
        // Ask-to-Buy — inform the user to wait for parental approval
        showToast('Your purchase is awaiting approval.');
      } else if (e instanceof ProductNotAvailableError) {
        // Product not available in this storefront
        showToast('This product is not available in your region.');
      } else if (e instanceof ReceiptInvalidError) {
        // Receipt validation failed — offer a retry
        showRetryPrompt();
      } else if (e instanceof NetworkUnavailableError) {
        showToast('No internet connection. Please try again.');
      } else {
        throw e; // re-throw unexpected errors
      }
    }
    ```
  </Tab>
  <Tab value="Swift">
    ```swift
    import Rovenue

    // --- Purchase flow ---
    do {
      let result = try await Rovenue.shared.purchase(pkg)
      // success
    } catch Rovenue.Error.purchaseCancelled {
      // User dismissed the store sheet — no action needed
    } catch Rovenue.Error.purchasePending {
      // Ask-to-Buy — inform the user to wait for parental approval
      showToast("Your purchase is awaiting approval.")
    } catch Rovenue.Error.productNotAvailable {
      showToast("This product is not available in your region.")
    } catch Rovenue.Error.receiptInvalid {
      // Receipt validation failed — offer a retry
      showRetryPrompt()
    } catch Rovenue.Error.networkUnavailable {
      showToast("No internet connection. Please try again.")
    } catch {
      throw error // re-throw unexpected errors
    }
    ```
  </Tab>
  <Tab value="Kotlin">
    ```kotlin
    import dev.rovenue.sdk.Rovenue
    import dev.rovenue.sdk.RovenueException
    import dev.rovenue.sdk.generated.ErrorKind

    // --- Purchase flow ---
    try {
        // `activity` is your current Activity — Play Billing requires it.
        val result = Rovenue.shared.purchase(activity, pkg)
        // success — check result.isDeferred for Ask-to-Buy (see below;
        // it does not throw)
    } catch (e: RovenueException) {
        when (e.kind) {
            ErrorKind.PURCHASE_CANCELED -> {
                // User dismissed the store sheet — no action needed
            }
            ErrorKind.PRODUCT_NOT_AVAILABLE -> {
                showToast("This product is not available in your region.")
            }
            ErrorKind.RECEIPT_INVALID -> {
                showRetryPrompt()
            }
            ErrorKind.NETWORK_UNAVAILABLE -> {
                showToast("No internet connection. Please try again.")
            }
            else -> throw e // re-throw unexpected SDK errors
        }
    }
    ```
  </Tab>
</Tabs>

<Callout type="info">
`PurchaseCancelledError` is **not an error** from the user's perspective. It fires whenever the store sheet is dismissed without a completed payment — including when the user deliberately taps Cancel. Do not show an error dialog for this case.
</Callout>

## Which methods throw which errors

| Method | Possible errors |
|--------|----------------|
| [`configure()`](/docs/reference/methods#configuration) | `InvalidApiKeyError` |
| [`identify(appUserId)`](/docs/reference/methods#identify) | `InvalidArgumentError` |
| [`refreshEntitlements()`](/docs/reference/methods#refreshentitlements) | `NetworkUnavailableError`, `ServerError` |
| [`refreshVirtualCurrencies()`](/docs/reference/methods#refreshvirtualcurrencies) | `NetworkUnavailableError`, `ServerError` |
| [`getOfferings()`](/docs/reference/methods#getofferings) | `NetworkUnavailableError`, `ServerError` |
| [`purchase()`](/docs/reference/methods#purchase) | `PurchaseCancelledError`, `PurchasePendingError`, `ProductNotAvailableError`, `StoreProblemError`, `ReceiptInvalidError`, `NetworkUnavailableError` |
| [`restorePurchases()`](/docs/reference/methods#restorepurchases) | `NetworkUnavailableError`, `ServerError` |
| [`getAppAccountToken()`](/docs/reference/methods#account-token) | `StorageError` |
| All methods | `InternalError` (unexpected failures) — see [Calling the SDK before `configure()`](#calling-the-sdk-before-configure) for what happens if `configure()` was skipped; it is not one of these errors |
